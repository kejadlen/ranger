# Tag cloud and task relationships

**Status:** Proposal. Not scheduled; written down to think through the shape of the change before deciding whether to do it. The ordering design in Part 2 was checked against an interactive prototype on 2026-11-03 and then revised: priority moved from `before` edges back to a position, now scoped to siblings. The decisions this settled are folded in below, and the questions it raised are under [Open questions](#open-questions).

This document proposes four changes to Ranger's data model:

- Replace backlogs with a single pool of tasks organized by `key:value` tags. A backlog becomes a tag such as `project:ranger`, and the default backlog becomes a default filter.
- Separate hard constraints from priority. Blockers and subtasks form an acyclic graph that every listing respects, with each subtask implicitly blocking its parent, and a position scoped to siblings ranks the tasks that are free to go next.
- Record each task's state changes as a history instead of a single `done_at` timestamp.
- Give each task a definition of done as its own field rather than prose buried in the description.

The changes are independent. None needs the others, and shipping the first two together would multiply the risk in `src/ops/task.rs`, which holds both the backlog scoping and the ordering logic. Treat them as separate projects.

Out of scope: multi-user features, saved views, and deriving task state from relationships (see [Relationships don't change state](#relationships-dont-change-state)).

## Background

Today every task belongs to exactly one backlog. `tasks.backlog_id` and `tasks.position` live on the task row, and `position` is a lexicographic fractional index scoped to the backlog, maintained by `src/position.rs`. Tags are free-form labels in a `tags` table joined through `task_tags`.

Ranger has tried relationships before. The initial schema had `tasks.parent_id` and a `blockers` table. Migration `005_drop_tags_blockers.sql` dropped blockers, `008_drop_parent_id.sql` dropped `parent_id`, and `009_task_edges.sql` added a `task_edges` table with the edge kinds `blocks` and `before` that `011_drop_task_edges.sql` removed. The design below is closest to the original `blockers` table and `parent_id` column, so the reason they didn't stick is the first thing to establish. It leaves out the `before` edges that 009 added, for the reasons in [Two kinds of ordering](#two-kinds-of-ordering).

## Part 1: tags replace backlogs

### Tags store their parsed key and value

Store the parse alongside the name:

```sql
CREATE TABLE tags (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL UNIQUE,
    key TEXT,   -- NULL for bare tags such as `bug`
    value TEXT
);
```

Split on the first colon when a tag is created. Queries such as "every `project:` value" and shell completion for tag values then read columns instead of repeating `substr`/`instr` in every call site.

The schema doesn't limit a task to one value per key. A task may carry both `project:ranger` and `project:dotfiles`; that flexibility is the main reason to drop backlogs. Per-key exclusivity could be added later as a policy, but it isn't part of this proposal.

### Filters are a small term language

A filter is a space-separated conjunction of terms:

```
project:ranger -someday state:ready
```

- A bare term (`bug`) or a `key:value` term matches tasks with that tag.
- A leading `-` negates a term.
- `state:` matches task state rather than a tag.
- `blocked:` matches whether a task has unfinished explicit blockers: `blocks` edges from tasks that aren't done. Open subtasks don't count (see [Subtasks block their parent](#subtasks-block-their-parent)).
- `depth:N` matches tasks with at most N ancestors in the subtask tree, so `depth:0` lists only top-level tasks. Without a `depth:` term, every level is listed.
- `expand:<key>` lists the direct subtasks of one parent that `depth:` would otherwise hide. It widens `depth:` rather than narrowing the match, so it has no effect without a `depth:` term. Keys resolve by unique prefix, and `expand:a|b` expands several parents. Expanding a subtask that is listed only because its parent is expanded goes one level further. `-expand:` has no meaning and is rejected.

There is no OR and no grouping. Same-key alternation (`project:ranger|dotfiles`, `state:ready|in_progress`) covers most cases without a real parser. The existing `--state` and `--tag` flags stay as shorthand that appends terms.

`RANGER_DEFAULT_FILTER` replaces `RANGER_DEFAULT_BACKLOG`. Ranger has one user, so the old variable can be dropped rather than deprecated. An empty or unset filter matches every task.

`task create` attaches the default filter's positive tag terms to the new task, so creating a task under `project:ranger` tags it `project:ranger`. An alternation term contributes its first value, so `project:ranger|dotfiles` tags the task `project:ranger`. That is the smallest set of tags that keeps the new task in the listing it was created from. Negated terms and non-tag terms (`state:`, `blocked:`, `depth:`, `expand:`) attach nothing. When the filter constrains `state:` and the command doesn't pass `--state`, the task gets the first state the filter allows, for the same reason.

This couples what you look at with what you write: a filter of `project:ranger bug` tags every new task as a bug. An earlier draft avoided that with a separate `RANGER_DEFAULT_TAGS` variable. Inheriting from the filter was chosen instead, because a task that disappears from the listing it was just created in is the more confusing failure. See [Open questions](#open-questions).

### Key lookup ignores the default filter

Today `RANGER_DEFAULT_BACKLOG` also scopes task key lookup, so a key that exists in another backlog fails with `no key matching prefix`. The `ranger` skill documents this as a gotcha. The default filter should affect listing only. Keys are globally unique, and shortest-prefix computation already runs over all keys through `ops::task::all_keys`, so resolving keys globally removes the gotcha without new ambiguity.

### Migration

The data moves mechanically:

1. Create one `project:<name>` tag per backlog.
2. Attach each task to the tag for its backlog.
3. Recreate `tasks` without `backlog_id`.

Recreating `tasks` must run inside `PRAGMA foreign_keys = OFF` / `ON`, as migrations 008, 010, and 013 do, or the `ON DELETE CASCADE` on `task_tags` deletes every tag association.

Positions survive this part, but dropping `backlog_id` merges every backlog's positions into one top-level sequence. Keys from different backlogs would interleave in string order and can collide, so the merge rebalances the combined set, one backlog after another, so each project's ranked tasks stay together. Generating fractional keys in SQL is awkward, so the rebalance belongs in Rust (`ops::task::rebalance` over the merged set) after the SQL migration has run.

## Part 2: blockers constrain order, positions rank siblings

### Two kinds of ordering

A task list answers two different questions. Some orderings are hard constraints: B can't start until A is done, and a parent isn't done until its subtasks are. Others are preferences: of the tasks that could go next, which matters most. An earlier draft of this proposal stored both as edges in one table, with `before` edges for priority beside `blocks` edges. A prototype showed that the priority edges caused most of the trouble:

- A move records an edge, and the tiebreak then re-sorts the task among everything it's no longer ordered against, so moving a task up one row can send it to the top of its group.
- Moving a task above a neighbor it was ordered after needs the old edge deleted or flipped, and flipping can remove the only path that ordered other tasks.
- Placing a task between two others records two edges, which ranks those two against each other even when nobody decided that.
- A filter that hides a task in the middle of a chain reorders the visible tasks unless order is resolved over the full graph first.

Blockers had none of these problems. So this part keeps the two apart: blockers and subtasks form a graph that every listing respects, and a stored position breaks ties among the tasks that are free to go next.

### Priority stays a position

`tasks.position` stays, with the same lexicographic fractional indexing in `src/position.rs`. What changes is its scope: positions order siblings, meaning tasks with the same `parent_id`, rather than tasks in the same backlog. Top-level tasks are ranked against each other, and each parent's subtasks are ranked against each other. A position never compares a task with one that isn't its sibling.

A stored position does what a move looks like it does. Dropping a task between two siblings computes a key between theirs, the task lands there, and it stays until it's moved again. Filtering can't change it, because a key means the same thing whichever tasks are visible.

The cost is that the top level is one sequence across every project, so a `project:ranger` task and a `project:dotfiles` task have a relative order even if nobody weighed them against each other. That was the earlier draft's objection to positions. It now applies only at the top level, and ranking mostly happens inside a filtered view, where a key placed between two visible siblings is still valid against the hidden ones.

Pairwise rating models such as TrueSkill were considered for priority. They record judgments rather than commands, and their uncertainty can suggest what to compare next. But a drag then needs several synthetic rounds to land where it was dropped, a rating can drift after later judgments, and most sibling sets are too small for the uncertainty to say much. Rating could come back later as a triage tool that writes positions, without changing this model.

### Blockers

```sql
CREATE TABLE task_blockers (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    blocker_id INTEGER NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
    blocked_id INTEGER NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
    created_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now')),
    UNIQUE (blocker_id, blocked_id)
);
```

"A blocks B" says B can't start until A is done. With priority out of the table there is only one kind of edge, so there's no `kind` column.

### Subtasks block their parent

Subtasks get a nullable `parent_id` column on `tasks`, which enforces the one-parent rule in the schema for free. They stay out of `task_blockers`, but each one implies a blocker edge from the subtask to its parent, because a parent isn't finished until its subtasks are. The implied edge is derived from `parent_id` whenever the graph is built and is never written to `task_blockers`.

The implied edge counts wherever order does: in the cycle check and in the linearization. It doesn't count for the `blocked:` filter term or the blocked marker in listings, which cover explicit blockers only. A parent with open subtasks is waiting on its own work, not on something else, and counting it as blocked would make `-blocked:true` hide every unfinished parent. Listings show a parent's open subtasks as a count instead.

Three consequences follow:

- The list is flat. A parent ranks below its open subtasks, so indenting children under their parent would contradict the order. A subtree isn't guaranteed to be contiguous in the order anyway: if subtask A blocks X and X blocks subtask B, no indented block can place X correctly. Each subtask names its parent instead, and `depth:` and `expand:` control how much of the tree a listing shows. The graph view is where the tree is visible as structure.
- Subtasks don't take their parent's priority. A subtask's position ranks it only among its siblings. In the flat list it does take its parent's place (see [Linearization](#linearization)), but its own position is unaffected.
- Explicit blockers between a task and its own ancestors are settled. An ancestor that blocks one of its descendants forms a cycle with the implied edges and is rejected. A descendant that blocks an ancestor is already implied, so it's redundant but harmless.

### Blockers must be acyclic

The check runs in the transaction that adds the blocker: before inserting "A blocks B", test whether A is already reachable from B through blockers and the edges implied by subtasks, and reject the insert if it is. Setting a parent adds an implied edge from the child to the new parent, so it runs the same check and rejects the change if the child is reachable from the new parent. Because implied edges link every subtask to its parent, that check also catches a loop in the subtask tree, so no separate walk of the ancestor chain is needed.

Positions never take part in the check. A preference can't contradict a constraint; it just loses to it.

### Linearization

Listing tasks sorts the filtered set with a stable topological sort, Kahn's algorithm over a priority queue. The edges are the blockers plus the implied subtask edges. Among the tasks whose incoming edges are all satisfied, take the one that sorts first by sibling path:

- If the two tasks are siblings, compare their positions.
- Otherwise, walk up from each task to the pair of ancestors that are siblings of each other, and compare those positions. A subtask of a highly ranked parent therefore comes before a task ranked below that parent.
- Equal positions fall back to `key`.

A task never competes with its own ancestor: a parent waits on its open subtasks, so it isn't available while any of them is. The result is the subtask tree walked with children before their parent, in position order at every level, with blockers overriding it wherever they apply.

The order has to be deterministic and documented, because the `ranger` skill instructs agents to pick up the top task when told to keep working.

Priority doesn't flow back through blockers. An important task waiting on a low-ranked blocker sits wherever the blocker's rank lets it, so the fix is to rank the blocker higher. Whether Ranger should do that itself is an [open question](#open-questions).

Filtering happens after order is resolved, not before. Reachability through blockers and subtask edges is computed over the full graph and then restricted to the filtered set, so a hidden task in the middle of a blocker chain still orders the visible tasks around it: given `A blocks X` and `X blocks B`, a filter that hides X still lists A above B. The same rule applies to subtasks hidden by `depth:`: their implied edges still order their parent.

State grouping happens at display time: group by state, then linearize within each group. A state change still re-places the task the way `ops::task::reorder` does today, scoped to its siblings instead of its backlog. `list --state done` continues to order by `done_at` (now derived; see [Part 3](#part-3-state-changes-are-recorded)) and ignores blockers entirely.

Blockers between tasks in different state groups have no effect on the list. In particular, the top `ready` task can be blocked by an `icebox` task. Agents that pick up the top task should list with `-blocked:true`, and the `ranger` skill should say so.

### The graph and the list are two views

The graph view (rollout step 7) shows the constraints: blockers and subtasks, transitively reduced. The list shows the order that results once positions break the ties. Priority doesn't appear in the graph.

The prototype laid the graph out in columns by depth, meaning the longest chain of edges leading into each task. Tasks with no edges get a column of their own, and tasks within a column are stacked in list order. A constraint that passes through a hidden task is drawn as its own kind of edge.

### Stored blockers are never reduced

Blockers are kept as stated, even when another path implies them. Given `A blocks B`, adding `A blocks X` and `X blocks B` makes the first blocker redundant. Leave it in place: if X is later deleted, A still blocks B, as was stated.

Transitive reduction applies to *display* only — drawing the graph without redundant edges — and the reduced graph is never written back.

### Where petgraph fits

Deriving order means running graph algorithms on every list command, which justifies a real graph library. petgraph covers two of the three needs:

| Need | Source |
|---|---|
| Cycle detection on blocker insert | petgraph, or a recursive CTE in SQL |
| Transitive reduction for the graph view | petgraph (`algo::tred`) |
| Stable topological sort | Hand-rolled; `algo::toposort` breaks ties by traversal order, not by sibling path |

Graph size is bounded by the number of tasks, so building it in memory per command costs nothing measurable at Ranger's scale. The mapping between task IDs and petgraph node indices has to be maintained on every build.

### CLI surface

`task move <key> -B <anchor>` and `-A <anchor>` keep their spelling and their meaning: each computes a position next to the anchor. The anchor must be a sibling of the task, since positions only rank siblings, and an anchor that isn't one is rejected with a message that names the task's parent. Changing a task's parent is a separate operation, not a move.

Because order is derived, a move can be a visual no-op: placing a task above something that blocks it changes its position but can't change the rendering. That case needs to say so rather than silently succeeding; see the `writing-error-messages` skill when wording it.

In the web UI, a drag in the flat list computes the new position from the nearest siblings above and below the drop point, which aren't always the rows directly next to it.

### Migration

Add `parent_id` as a nullable column and create `task_blockers`. Positions need no conversion: every existing task becomes top-level, so its position already ranks it among its new siblings.

`ops::task::reorder`, `ops::task::rebalance`, and the position helpers `next_position_after`, `prev_position_before`, `last_position_in_state`, and `first_position_in_state` change their scope from `backlog_id` to `parent_id`. If Part 2 ships before Part 1, the scope is the pair until Part 1 drops `backlog_id`.

### Relationships don't change state

Relationships are displayed, not enforced on state. Ranger won't mark a parent done when its children finish, and it won't prevent a blocked task from being `ready`. Derived state tends to produce constraints like the existing `CHECK ((state = 'done') = (done_at IS NOT NULL))`, multiplied across the graph. Instead, `task show` lists blockers and subtasks, and the `blocked:` filter term makes `-blocked:true` list only unblocked work.

Ordering is the one exception: blockers and subtasks constrain the order a listing shows, but that order is derived at display time, so nothing has to stay consistent on disk.

## Part 3: state changes are recorded

### Why state gets a history

State is already a field on the task rather than a tag, which is what makes `state:` filtering and state grouping possible. What Ranger doesn't keep is how a task got there. It stores the current state and, for done tasks, a `done_at` timestamp, so when a task became `ready`, how long it was `in_progress`, and whether it was ever reopened are all lost.

### Schema

```sql
CREATE TABLE task_transitions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    task_id INTEGER NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
    state TEXT NOT NULL,
    at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now'))
);
```

Creating a task appends its initial state, and every state change appends a row with the new state. The log is append-only. `tasks.state` stays as the current state, so filtering never reads the log.

`done_at` becomes derived: it's the time of the latest transition into `done`. The column goes away, and so does the `CHECK ((state = 'done') = (done_at IS NOT NULL))` constraint. Reopening a task no longer has to clear a timestamp, and the earlier completion stays in the history.

Only explicit state changes write to the log. Nothing derived from relationships does, which keeps this consistent with [Relationships don't change state](#relationships-dont-change-state): finishing a parent's last subtask records nothing on the parent.

### Migration

Seed one row per existing task with its current state, timestamped with `done_at` for done tasks and `created_at` otherwise. History from before the migration can't be recovered. Dropping `done_at` recreates `tasks`, so it needs the `PRAGMA foreign_keys = OFF` / `ON` wrapper.

### CLI surface

`task show` lists the history, newest first, after the current state. The web UI's task detail view does the same.

### Affected code

`migrations/`, `src/models.rs` (`Task` loses `done_at` as a stored field), `src/ops/task.rs` (every state change appends a transition, and `done_at` is read from the log), `src/bin/ranger/commands/task.rs` (`print_task_detail`), and the task detail view in `serve.rs`.

## Part 4: a definition of done

### Why it gets its own field

A task today has a title and a free-form description, so whatever says when the task is finished is mixed into the description, if it's written down at all. The `ranger` skill tells agents to pick up the top task and keep working, which makes "how do I know I'm done" the question an agent most needs answered and the one Ranger gives it least help with. A separate field makes the criteria something Ranger can display, prompt for, and filter on.

### Schema

Add one nullable column:

```sql
ALTER TABLE tasks ADD COLUMN done_when TEXT;
```

It's free-form text, like `description`. Structured checklists with per-item completion are out of scope; they would bring back the derived-state problem described in [Relationships don't change state](#relationships-dont-change-state). Because this is a plain `ADD COLUMN`, the migration doesn't recreate `tasks` and needs no `PRAGMA foreign_keys` dance. Existing tasks get `NULL`.

### CLI surface

- `task create` and `task edit` take `--done-when <text>`.
- `task show` prints the field after the description, labeled `Done when:`.
- The editor flow in `edit_in_editor` currently treats the first line as the title and everything else as the description. It needs a marker line, such as `Done when:`, that splits the body into description and definition of done. A missing marker leaves the field unchanged, and a marker with nothing under it clears the field.
- The filter language from Part 1 gains a term for tasks without a definition, such as `-has:done_when`, so the gaps are easy to find.

### Ranger records the definition but doesn't check it

Marking a task done doesn't verify the criteria; Ranger can't, and pretending to would be worse than not trying. The `ranger` skill changes instead: agents read `done_when` before starting a task and confirm each criterion before marking it done.

### Affected code

`migrations/`, `src/models.rs` (`Task`), `src/ops/task.rs` (`create` and `edit`), `src/bin/ranger/commands/task.rs` (flags, `print_task_detail`, and the editor parser), the task detail view in `serve.rs`, and `skills/ranger/SKILL.md`. The editor parser's marker handling is the main new branching under the coverage gate.

## Rollout

Each step leaves the build green and can ship on its own:

1. Add `key` and `value` columns to `tags`. No behavior change.
2. Add the filter language as shorthand over the existing flags, still scoped to a backlog.
3. Mirror each backlog into a `project:` tag and write both on every change.
4. Drop `backlog_id`, the backlog commands, and `RANGER_DEFAULT_BACKLOG`.
5. Add `task_blockers`, `parent_id`, the implied subtask edges, and the cycle check, and scope positions to siblings, with listing still in position order. The `depth:` and `expand:` filter terms land here, since they need `parent_id`.
6. Switch listing to the derived order: Kahn's algorithm over blockers and subtask edges, with sibling path as the tiebreak.
7. Add the graph view with transitive reduction.

Steps 1 through 3 are reversible. No step discards ordering data now that positions stay. Step 4 is the hardest to undo, because it drops `backlog_id` and rebalances positions, but the `project:` tags carry the same information.

Parts 3 and 4 don't depend on either sequence and can ship before, between, or after them. Only Part 4's `has:` filter term waits for step 2.

## Open questions

- Why were `blockers`, `parent_id`, and `task_edges` dropped in migrations 005, 008, and 011? This proposal rebuilds the original `blockers` table and `parent_id` almost exactly, so whatever made them not worth keeping applies here too.
- Should priority flow back through blockers? An important task waiting on a low-ranked blocker sits wherever the blocker's rank lets it. Ranger could rank each blocker at least as high as the tasks it blocks, at the cost of an order you didn't set.
- Is one top-level sequence across every project acceptable? A drag in a filtered view also ranks the task against hidden siblings that fall between its new neighbors.
- Is inheriting the default filter's tags on create the right default, given that `project:ranger bug` tags every new task a bug? A separate `RANGER_DEFAULT_TAGS` variable decouples the two, at the cost of tasks that vanish from the listing they were created in.
- Now that `blocked:` ignores subtasks, should "has open subtasks" be a filter term of its own, such as `has:open-subtasks`?
- Should moving a task to `ready` require a definition of done? That would make the field a gate rather than a convention, at the cost of breaking `task create --state ready` for quick captures.
