# Tag cloud and task relationships

**Status:** Proposal. Not scheduled; written down to think through the shape of the change before deciding whether to do it. The ordering design in Part 2 was checked against an interactive prototype on 2026-11-03. The decisions it settled are folded in below, and the questions it raised are under [Open questions](#open-questions).

This document proposes four changes to Ranger's data model:

- Replace backlogs with a single pool of tasks organized by `key:value` tags. A backlog becomes a tag such as `project:ranger`, and the default backlog becomes a default filter.
- Replace stored positions with a graph of task relationships. Blockers and priority are both edges, task order is derived from them, and the graph must be acyclic. Subtasks form a tree, and each subtask implicitly blocks its parent.
- Record each task's state changes as a history instead of a single `done_at` timestamp.
- Give each task a definition of done as its own field rather than prose buried in the description.

The changes are independent. None needs the others, and shipping the first two together would multiply the risk in `src/ops/task.rs`, which holds both the backlog scoping and the ordering logic. Treat them as separate projects.

Out of scope: multi-user features, saved views, and deriving task state from relationships (see [Relationships don't change state](#relationships-dont-change-state)).

## Background

Today every task belongs to exactly one backlog. `tasks.backlog_id` and `tasks.position` live on the task row, and `position` is a lexicographic fractional index scoped to the backlog, maintained by `src/position.rs`. Tags are free-form labels in a `tags` table joined through `task_tags`.

Ranger has tried relationships before. The initial schema had `tasks.parent_id` and a `blockers` table. Migration `005_drop_tags_blockers.sql` dropped blockers, `008_drop_parent_id.sql` dropped `parent_id`, and `009_task_edges.sql` added a `task_edges` table with the edge kinds `blocks` and `before` that `011_drop_task_edges.sql` removed. The design below is close to that dropped table, so the reason it didn't stick is the first thing to establish.

## Part 1: tags replace backlogs

### Tags store their parsed key and value

Store the parse alongside the name:

```sql
CREATE TABLE tags (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL UNIQUE,
    key TEXT,   -- NULL for bare tags such as `bug`
    value TEXT
);
```

Split on the first colon when a tag is created. Queries such as "every `project:` value" and shell completion for tag values then read columns instead of repeating `substr`/`instr` in every call site.

The schema doesn't limit a task to one value per key. A task may carry both `project:ranger` and `project:dotfiles`; that flexibility is the main reason to drop backlogs. Per-key exclusivity could be added later as a policy, but it isn't part of this proposal.

### Filters are a small term language

A filter is a space-separated conjunction of terms:

```
project:ranger -someday state:ready
```

- A bare term (`bug`) or a `key:value` term matches tasks with that tag.
- A leading `-` negates a term.
- `state:` matches task state rather than a tag.
- `blocked:` matches whether a task has unfinished explicit blockers: `blocks` edges from tasks that aren't done. Open subtasks don't count (see [Subtasks block their parent](#subtasks-block-their-parent)).
- `depth:N` matches tasks with at most N ancestors in the subtask tree, so `depth:0` lists only top-level tasks. Without a `depth:` term, every level is listed.
- `expand:<key>` lists the direct subtasks of one parent that `depth:` would otherwise hide. It widens `depth:` rather than narrowing the match, so it has no effect without a `depth:` term. Keys resolve by unique prefix, and `expand:a|b` expands several parents. Expanding a subtask that is listed only because its parent is expanded goes one level further. `-expand:` has no meaning and is rejected.

There is no OR and no grouping. Same-key alternation (`project:ranger|dotfiles`, `state:ready|in_progress`) covers most cases without a real parser. The existing `--state` and `--tag` flags stay as shorthand that appends terms.

`RANGER_DEFAULT_FILTER` replaces `RANGER_DEFAULT_BACKLOG`. Ranger has one user, so the old variable can be dropped rather than deprecated. An empty or unset filter matches every task.

`task create` attaches the default filter's positive tag terms to the new task, so creating a task under `project:ranger` tags it `project:ranger`. An alternation term contributes its first value, so `project:ranger|dotfiles` tags the task `project:ranger`. That is the smallest set of tags that keeps the new task in the listing it was created from. Negated terms and non-tag terms (`state:`, `blocked:`, `depth:`, `expand:`) attach nothing. When the filter constrains `state:` and the command doesn't pass `--state`, the task gets the first state the filter allows, for the same reason.

This couples what you look at with what you write: a filter of `project:ranger bug` tags every new task as a bug. An earlier draft avoided that with a separate `RANGER_DEFAULT_TAGS` variable. Inheriting from the filter was chosen instead, because a task that disappears from the listing it was just created in is the more confusing failure. See [Open questions](#open-questions).

### Key lookup ignores the default filter

Today `RANGER_DEFAULT_BACKLOG` also scopes task key lookup, so a key that exists in another backlog fails with `no key matching prefix`. The `ranger` skill documents this as a gotcha. The default filter should affect listing only. Keys are globally unique, and shortest-prefix computation already runs over all keys through `ops::task::all_keys`, so resolving keys globally removes the gotcha without new ambiguity.

### Migration

The data moves mechanically:

1. Create one `project:<name>` tag per backlog.
2. Attach each task to the tag for its backlog.
3. Recreate `tasks` without `backlog_id`.

Recreating `tasks` must run inside `PRAGMA foreign_keys = OFF` / `ON`, as migrations 008, 010, and 013 do, or the `ON DELETE CASCADE` on `task_tags` deletes every tag association.

Positions survive this part unchanged. Part 2 replaces them, and the two migrations should not be combined — converting positions to edges while `backlog_id` is still present keeps each chain scoped to a backlog, which is what makes the conversion meaningful.

## Part 2: order comes from edges

### Why positions go away

Ranger's stored `position` asserts a total order: every task is comparable to every other task, including tasks in unrelated projects that were never weighed against each other. Most of that order is invented. What actually gets decided is relative — "this before that" — so the model should store the comparisons that were made and nothing else.

The consequence is that task order becomes a partial order, and any list has to linearize it. That linearization is arbitrary wherever no comparison exists, so the tiebreak is part of the design rather than an implementation detail.

### One table for order-bearing edges

Blockers and priority differ in meaning but not in shape. "A blocks B" says B cannot start until A is done; "A before B" says B matters less. Both constrain order in the same direction, and the linearization consumes their union, so they share a table:

```sql
CREATE TABLE task_edges (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    from_task_id INTEGER NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
    to_task_id INTEGER NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
    kind TEXT NOT NULL CHECK (kind IN ('blocks', 'before')),
    created_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now')),
    UNIQUE (from_task_id, to_task_id, kind)
);
```

### Subtasks block their parent

Subtasks get a nullable `parent_id` column on `tasks`, which enforces the one-parent rule in the schema for free. They stay out of `task_edges`, but each one implies a `blocks` edge from the subtask to its parent, because a parent isn't finished until its subtasks are. The implied edge is derived from `parent_id` whenever the graph is built and is never written to `task_edges`.

The implied edge counts wherever order does: in the cycle check and in the linearization. It doesn't count for the `blocked:` filter term or the blocked marker in listings, which cover explicit `blocks` edges only. A parent with open subtasks is waiting on its own work, not on something else, and counting it as blocked would make `-blocked:true` hide every unfinished parent. Listings show a parent's open subtasks as a count instead.

Two consequences follow:

- The list is flat. A parent ranks below its open subtasks, so indenting children under their parent would contradict the order. A subtree isn't guaranteed to be contiguous in the order anyway: if subtask A comes before X and X comes before subtask B, no indented block can place X correctly. Each subtask names its parent instead, and `depth:` and `expand:` control how much of the tree a listing shows. The graph view is where the tree is visible as structure.
- Explicit edges between a task and its own ancestors are settled. An ancestor that blocks or comes before one of its descendants forms a cycle with the implied edges and is rejected. A descendant that blocks an ancestor is already implied, so it's redundant but harmless.

### Acyclicity is checked across kinds

The cycle check runs on the union of both edge kinds, not on each kind separately. "A blocks B" together with "B before A" is contradictory as an ordering even though each edge is individually fine, so checking the kinds independently would admit orders that cannot be linearized.

The check runs in the transaction that adds the edge: before inserting an edge from A to B, test whether A is already reachable from B through edges of either kind, including the edges implied by subtasks, and reject the insert if it is. Setting a parent adds an implied edge from the child to the new parent, so it runs the same check and rejects the change if the child is reachable from the new parent. Because implied edges link every subtask to its parent, that check also catches a loop in the subtask tree, so no separate walk of the ancestor chain is needed.

### Linearization

Listing tasks sorts the filtered set with a stable topological sort — Kahn's algorithm over a priority queue. Among the tasks whose incoming edges are all satisfied, take the one that sorts first by `created_at`, then by `key`.

The tiebreak has to be deterministic and documented, not incidental. A partial order can have several maximal elements, so "the top of the queue" is otherwise ambiguous, and the `ranger` skill instructs agents to pick up the top task when told to keep working. Oldest-first is the tiebreak that makes an unranked backlog behave like a queue.

Filtering happens after order is resolved, not before. Reachability is computed over the full graph and then restricted to the filtered set, so a hidden task in the middle of a chain still orders the visible tasks around it: given `A before X` and `X before B`, a filter that hides X still lists A above B. Linearizing only the edges between visible tasks would let a filter reorder a list, so the same two tasks could appear in different orders depending on how you look at them. The same rule applies to subtasks hidden by `depth:`: their implied edges still order their parent.

State grouping happens at display time: group by state, then linearize within each group. This replaces `ops::task::reorder`, which today rewrites a task's position when its state changes. `list --state done` continues to order by `done_at` (now derived; see [Part 3](#part-3-state-changes-are-recorded)) and ignores edges entirely.

Edges between tasks in different state groups have no effect on the list. In particular, the top `ready` task can be blocked by an `icebox` task. Agents that pick up the top task should list with `-blocked:true`, and the `ranger` skill should say so.

### The graph and the list are two views of one model

The graph is the model, and the list is its projection to one dimension. The web UI shows both: the graph view (rollout step 7) shows what has actually been decided, and the list shows the order that results.

The prototype's graph lays tasks out in columns by depth in the partial order, meaning the longest chain of edges leading into each task. Tasks with no edges get a column of their own, and tasks within a column are stacked in list order. Tasks in the same column are unranked against each other, so the columns show where the tiebreak is deciding. The graph draws an order that passes through a hidden task as its own kind of edge.

The list doesn't mark where the tiebreak decided. The prototype tried a divider between adjacent unranked rows, and it was more confusing than useful.

### Stored edges are never reduced

Inserting a task between two others creates redundant edges. Given `A before B`, placing X between them adds `A before X` and `X before B`, and `A before B` is now implied by the path through X.

Leave it in place. Deleting it would lose information that was stated explicitly: if X is later deleted, A and B silently become unordered. Keeping every stated edge means deleting a task in the middle of a chain splices that chain automatically, because the edge spanning the gap is still there.

Transitive reduction applies to *display* only — drawing the relationship graph without redundant edges — and the reduced graph is never written back.

### Where petgraph fits

Deriving order means running graph algorithms on every list command, which justifies a real graph library. petgraph covers two of the three needs:

| Need | Source |
|---|---|
| Cycle detection on edge insert | petgraph, or a recursive CTE in SQL |
| Transitive reduction for the graph view | petgraph (`algo::tred`) |
| Stable topological sort | Hand-rolled; `algo::toposort` breaks ties by traversal order, not by `created_at` |

Graph size is bounded by the number of tasks, so building it in memory per command costs nothing measurable at Ranger's scale. The mapping between task IDs and petgraph node indices has to be maintained on every build.

### CLI surface

`task move <key> -B <anchor>` and `-A <anchor>` keep their spelling and change their meaning: each one now records a `before` edge rather than computing a position string. Placing between two anchors records two edges.

A move records the fewest edges that produce it, and records nothing when the requested order is already implied. It can still move a task more than one row: once the new edge is in place, the tiebreak re-sorts the task among the tasks it's no longer ordered against, so moving a task above its neighbor can release it to the top of its group. Edges don't change state, so a move only reorders within a state group.

Because order is derived, a move can be a visual no-op — asking for a task to sit above something that blocks it cannot change the rendering. That case needs to say so rather than silently succeeding; see the `writing-error-messages` skill when wording it.

### Migration

Convert each backlog's `ready` tasks into a chain of `before` edges, in position order, using `lead()` over `position` partitioned by `backlog_id`. Then drop `tasks.position`.

Only `ready` tasks get chained. Their order is the order that was deliberately maintained, so it's worth preserving exactly. Icebox tasks were mostly never ranked against each other — their positions are an artifact of insertion order, which the `created_at` tiebreak already reproduces — and chaining them would convert thousands of accidental positions into stated constraints that then have to be maintained by hand.

Dropping `position` also deletes `src/position.rs` (174 lines), `ops::task::rebalance`, `ops::task::reorder`, and the position helpers `next_position_after`, `prev_position_before`, `last_position_in_state`, and `first_position_in_state`.

### Relationships don't change state

Relationships are displayed, not enforced on state. Ranger won't mark a parent done when its children finish, and it won't prevent a blocked task from being `ready`. Derived state tends to produce constraints like the existing `CHECK ((state = 'done') = (done_at IS NOT NULL))`, multiplied across the graph. Instead, `task show` lists blockers and subtasks, and the `blocked:` filter term makes `-blocked:true` list only unblocked work.

Ordering is the one exception, and it is derived rather than stored, so nothing has to stay consistent on disk.

## Part 3: state changes are recorded

### Why state gets a history

State is already a field on the task rather than a tag, which is what makes `state:` filtering and state grouping possible. What Ranger doesn't keep is how a task got there. It stores the current state and, for done tasks, a `done_at` timestamp, so when a task became `ready`, how long it was `in_progress`, and whether it was ever reopened are all lost.

### Schema

```sql
CREATE TABLE task_transitions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    task_id INTEGER NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
    state TEXT NOT NULL,
    at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now'))
);
```

Creating a task appends its initial state, and every state change appends a row with the new state. The log is append-only. `tasks.state` stays as the current state, so filtering never reads the log.

`done_at` becomes derived: it's the time of the latest transition into `done`. The column goes away, and so does the `CHECK ((state = 'done') = (done_at IS NOT NULL))` constraint. Reopening a task no longer has to clear a timestamp, and the earlier completion stays in the history.

Only explicit state changes write to the log. Nothing derived from relationships does, which keeps this consistent with [Relationships don't change state](#relationships-dont-change-state): finishing a parent's last subtask records nothing on the parent.

### Migration

Seed one row per existing task with its current state, timestamped with `done_at` for done tasks and `created_at` otherwise. History from before the migration can't be recovered. Dropping `done_at` recreates `tasks`, so it needs the `PRAGMA foreign_keys = OFF` / `ON` wrapper.

### CLI surface

`task show` lists the history, newest first, after the current state. The web UI's task detail view does the same.

### Affected code

`migrations/`, `src/models.rs` (`Task` loses `done_at` as a stored field), `src/ops/task.rs` (every state change appends a transition, and `done_at` is read from the log), `src/bin/ranger/commands/task.rs` (`print_task_detail`), and the task detail view in `serve.rs`.

## Part 4: a definition of done

### Why it gets its own field

A task today has a title and a free-form description, so whatever says when the task is finished is mixed into the description, if it's written down at all. The `ranger` skill tells agents to pick up the top task and keep working, which makes "how do I know I'm done" the question an agent most needs answered and the one Ranger gives it least help with. A separate field makes the criteria something Ranger can display, prompt for, and filter on.

### Schema

Add one nullable column:

```sql
ALTER TABLE tasks ADD COLUMN done_when TEXT;
```

It's free-form text, like `description`. Structured checklists with per-item completion are out of scope; they would bring back the derived-state problem described in [Relationships don't change state](#relationships-dont-change-state). Because this is a plain `ADD COLUMN`, the migration doesn't recreate `tasks` and needs no `PRAGMA foreign_keys` dance. Existing tasks get `NULL`.

### CLI surface

- `task create` and `task edit` take `--done-when <text>`.
- `task show` prints the field after the description, labeled `Done when:`.
- The editor flow in `edit_in_editor` currently treats the first line as the title and everything else as the description. It needs a marker line, such as `Done when:`, that splits the body into description and definition of done. A missing marker leaves the field unchanged, and a marker with nothing under it clears the field.
- The filter language from Part 1 gains a term for tasks without a definition, such as `-has:done_when`, so the gaps are easy to find.

### Ranger records the definition but doesn't check it

Marking a task done doesn't verify the criteria; Ranger can't, and pretending to would be worse than not trying. The `ranger` skill changes instead: agents read `done_when` before starting a task and confirm each criterion before marking it done.

### Affected code

`migrations/`, `src/models.rs` (`Task`), `src/ops/task.rs` (`create` and `edit`), `src/bin/ranger/commands/task.rs` (flags, `print_task_detail`, and the editor parser), the task detail view in `serve.rs`, and `skills/ranger/SKILL.md`. The editor parser's marker handling is the main new branching under the coverage gate.

## Rollout

Each step leaves the build green and can ship on its own:

1. Add `key` and `value` columns to `tags`. No behavior change.
2. Add the filter language as shorthand over the existing flags, still scoped to a backlog.
3. Mirror each backlog into a `project:` tag and write both on every change.
4. Drop `backlog_id`, the backlog commands, and `RANGER_DEFAULT_BACKLOG`.
5. Add `task_edges`, `parent_id`, the implied subtask edges, and the cycle check, with order still coming from `position`. The `depth:` and `expand:` filter terms land here, since they need `parent_id`.
6. Switch listing to the derived order, convert `ready` positions to chains, and drop `position`.
7. Add the graph view with transitive reduction.

Steps 1 through 3 are reversible. Step 6 is the one that can't be undone without restoring positions from a backup.

Parts 3 and 4 don't depend on either sequence and can ship before, between, or after them. Only Part 4's `has:` filter term waits for step 2.

## Open questions

- Why were `blockers`, `parent_id`, and `task_edges` dropped in migrations 005, 008, and 011? This proposal rebuilds the `009` schema almost exactly, so whatever made it not worth keeping applies here too.
- Should the migration chain only `ready` tasks, as proposed above, or every task in position order? Chaining everything preserves today's list exactly, at the cost of turning incidental positions into stated constraints.
- Is `created_at` the right linearization tiebreak, or should unranked tasks sort newest-first?
- When a move contradicts a single direct `before` edge, should it replace that edge instead of being rejected? The prototype replaces it, so moving a task up works without deleting the old edge first. In the prototype, though, replacing `lfej before hwle` to move `hwle` up one row also removed the only path that ordered `vkmo` above `hwle`, and the tiebreak moved `hwle` from seventh to second.
- Should placing a task between two anchors be allowed to rank the anchors against each other? When the anchors were adjacent only by tiebreak, recording both edges orders them, which nobody asked for. Recording one edge avoids that but makes the move less precise.
- Should a move stay local? Because the tiebreak re-sorts a moved task, moving it one row can jump it several. Keeping moves local would make the tiebreak depend on the current list rather than on `created_at` alone.
- Is inheriting the default filter's tags on create the right default, given that `project:ranger bug` tags every new task a bug? A separate `RANGER_DEFAULT_TAGS` variable decouples the two, at the cost of tasks that vanish from the listing they were created in.
- Now that `blocked:` ignores subtasks, should "has open subtasks" be a filter term of its own, such as `has:open-subtasks`?
- Should moving a task to `ready` require a definition of done? That would make the field a gate rather than a convention, at the cost of breaking `task create --state ready` for quick captures.
